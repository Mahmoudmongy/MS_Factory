# النسخ الاحتياطي المشفّر والاستعادة — MS Factory

## الحالة الحالية

- قاعدة الإنتاج على Supabase Free؛ الخطة المجانية لا توفر نسخًا يومية تلقائية ولا Point-in-Time Recovery.
- تمت مراجعة قاعدة الإنتاج قراءةً فقط: PostgreSQL 17.11، مستخدم Auth واحد، وهوية واحدة، ولا توجد Storage buckets حاليًا.
- حساب Cloudflare يحتاج إلى تفعيل R2 من لوحة التحكم أولًا. طلب قراءة قائمة الحاويات أعاد رفضًا صريحًا لأن R2 غير مفعّل. لذلك لم يتم إنشاء حاوية أو رفع نسخة احتياطية بعد.
- سير العمل أدناه لا يبدأ تلقائيًا قبل ضبط المتغير `BACKUP_ENABLED=true`. لا يرفع أي شيء إلى مكان عام.

## بنية الحماية

1. تصدير الأدوار وSchema وبيانات قاعدة PostgreSQL باستخدام Supabase CLI.
2. تصدير بيانات Auth اللازمة لاسترجاع الحسابات (users/identities وعوامل MFA/Passkeys) بشكل منفصل، لأن Supabase CLI يستبعد مخططات Supabase المُدارة مثل `auth` و`storage`.
3. إرفاق trigger إنشاء profile بعد الاستعادة، ومجلد Edge Functions وترحيلات SQL.
4. حساب SHA-256 للملفات، ثم تشفير الأرشيف كاملًا باستخدام GPG AES-256 قبل خروجه من GitHub Actions.
5. رفع الملف المشفّر إلى حاوية Cloudflare R2 خاصة عبر S3 API، ثم تنزيله للتحقق من تطابق SHA-256.
6. الاحتفاظ بـ45 يومًا من النسخ اليومية و400 يوم من النسخ الشهرية. لا يتم الاحتفاظ بجلسات الدخول أو refresh tokens في النسخة.

كلمات المرور لا تُحفظ كنص صريح؛ بيانات Auth تحتوي على التجزئات السرية، ولذلك لا تغادر GitHub إلا داخل ملف مشفّر. مفتاح التشفير لا يوضع في المستودع ولا في R2.

## حدود التكلفة المجانية

اختر Standard storage فقط. الحصة المجانية الحالية لـ R2 تشمل 10 GB-month من التخزين، ومليون طلب Class A، و10 ملايين طلب Class B شهريًا، وبدون رسوم نقل بيانات للخارج. تجاوز الحصة يُحاسب؛ يجب مراقبة الاستخدام وعدم استخدام Infrequent Access لهذه النسخ.

## تفعيل النسخ الاحتياطي مرة واحدة

### أ) فعّل R2

من Cloudflare Dashboard:
1. افتح R2 Object Storage.
2. فعّل R2 على الحساب.
3. أنشئ حاوية باسم `ms-factory-secure-backups` في Standard storage.
4. اترك Public access و`r2.dev` معطّلين. لا تضف Custom Domain.
5. أنشئ R2 API token بصلاحية Object Read & Write لهذه الحاوية فقط.

### ب) أضف إعدادات GitHub

في المستودع:
**Settings → Secrets and variables → Actions**

Repository Variables:
- `BACKUP_ENABLED` = `true` (لا تضعها قبل إنشاء الحاوية وإضافة الأسرار)
- `SUPABASE_PROJECT_REF` = `yvrislcbbhtruwdnuooz`
- `R2_BUCKET` = `ms-factory-secure-backups`
- `R2_ENDPOINT` = `https://d6d9e923e57e3b039156162fc231617e.r2.cloudflarestorage.com`

Repository Secrets:
- `SUPABASE_DB_URL` = اتصال قاعدة البيانات من Supabase Connect، استخدم Session Pooler على منفذ 5432 أو الاتصال المباشر إن كان متاحًا. يجب أن تكون كلمة المرور URL-encoded.
- `R2_ACCESS_KEY_ID` = معرّف R2 API token.
- `R2_SECRET_ACCESS_KEY` = سر R2 API token.
- `BACKUP_GPG_PASSPHRASE` = عبارة مرور عشوائية قوية جدًا (32 حرفًا على الأقل).

احتفظ بعبارة المرور في مدير كلمات مرور موثوق أو نسخة ورقية محفوظة بمكان منفصل عن R2 وحساب GitHub. فقدانها يعني عدم إمكانية فك النسخ الاحتياطية. لا ترسلها في المحادثات ولا تضعها في أي ملف بالمستودع.

بعد ضبط القيم، شغّل workflow يدويًا مرة واحدة مع اختيار `Run confirmed`. راجع نجاح خطوة رفع R2 وقراءة الملف والتحقق من checksum. بعد ذلك يعمل الجدول اليومي تلقائيًا الساعة 02:20 UTC.

## الاستعادة عند الاختراق أو تلف البيانات

**لا تستعد فوق قاعدة الإنتاج المخترقة مباشرة.** أنشئ مشروع Supabase جديدًا للاستعادة حتى لا تفقد الأدلة أو النسخة المتبقية.

1. نزّل الملف المطلوب من R2 باستخدام R2 API token، واحتفظ بالملف الأصلي كما هو.
2. فك التشفير محليًا بعبارة المرور المحفوظة:
   `gpg --batch --pinentry-mode loopback --passphrase-file /secure/path/passphrase.txt --decrypt --output backup.tar.gz backup.tar.gz.gpg`
3. فك ضغط الأرشيف، ثم شغّل:
   `sha256sum -c SHA256SUMS`
   يجب أن تنجح جميع الفحوص قبل بدء الاستعادة.
4. جهّز مشروع Supabase جديدًا، وفعّل الإضافات المطلوبة إذا تغيّرت عن الافتراضي. لا تستخدم قاعدة الإنتاج الحالية كهدف أول.
5. طبّق الأدوار والـSchema والبيانات وبيانات Auth على المشروع الجديد باستخدام اتصال قاعدة البيانات الجديد:

   ```bash
   psql --single-transaction --variable ON_ERROR_STOP=1 \
     --file roles.sql \
     --file schema.sql \
     --command 'SET session_replication_role = replica' \
     --file auth-data.sql \
     --file data.sql \
     --dbname "$RESTORE_DB_URL"
   ```

6. أعد إنشاء trigger إنشاء profile:
   `psql "$RESTORE_DB_URL" --set ON_ERROR_STOP=1 --file auth-trigger.sql`
7. تحقق من أعداد المستخدمين والملفات الشخصية والعملاء والفواتير والأصناف وأوامر الإنتاج، وتأكد أن RLS مفعّل والسياسات والدوال موجودة.
8. انشر Edge Functions الموجودة في مجلد `functions` عبر Supabase CLI، وأعد ضبط أسرارها وإعدادات Auth/SMTP/Redirect URLs وRealtime يدويًا.
9. اختبر تسجيل دخول المدير والموظف، والمزامنة والعمليات المحاسبية على مشروع الاستعادة.
10. غيّر إعدادات الواجهة إلى URL وAnon Key الخاصين بالمشروع الجديد **بعد نجاح الاختبار فقط**. سيتطلب الأمر تسجيل دخول جديدًا لأن جلسات JWT القديمة لا تصلح للمشروع الجديد.

## ما لا يغطيه أرشيف قاعدة البيانات

- ملفات Storage الفعلية؛ حاليًا لا توجد أي Storage buckets. إذا أُنشئت مستقبلًا، يوقف workflow النسخ الاحتياطي عمدًا حتى نضيف نسخ ملفات حقيقية، وليس بيانات metadata فقط.
- إعدادات مزودي Auth وSMTP، مفاتيح API وJWT، إعدادات Realtime وDomains وبيئة Edge Functions secrets. تُحفظ وتُضبط منفصلة.
- نسخ جلسات المستخدم وRefresh Tokens؛ يجب على الجميع تسجيل الدخول من جديد بعد الاستعادة.

## اختبار الاستعادة

الـworkflow يتحقق من فك التشفير وSHA-256 وقراءة الملف من R2، لكنه **لا يعتبر ذلك اختبار استعادة كاملًا**. يلزم إجراء Restore Drill على مشروع/بيئة جديدة، ثم تشغيل اختبارات التطبيق والصلاحيات قبل اعتماد النسخة. لا نختبر الاستعادة على الإنتاج.

## سياسة التنبيه

أي فشل في النسخ يجعل GitHub Actions workflow أحمر. فعّل إشعارات GitHub Actions للمستودع وراجع سجل التشغيل اليومي. لا تعتبر وجود ملفات في R2 دليلًا كافيًا؛ يجب متابعة تاريخ آخر نسخة ناجحة والتحقق من ملف القراءة العكسية.
