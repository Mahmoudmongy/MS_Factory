# مراجعة MS Factory الشاملة — 9 نوفمبر 2026

## الملخص التنفيذي

البرنامج يعمل كواجهة PWA محلية مع ربط Supabase للمصادقة والمزامنة. نجاح الاختبارات الحالية لا يثبت اكتمال المزامنة المحاسبية متعددة الأجهزة أو أمان كل مسارات عرض البيانات. لا أوصي باعتبار الإصدار جاهزًا للتشغيل اليومي متعدد الموظفين قبل إغلاق الموانع عالية الخطورة أدناه.

## نتائج مؤكدة

### 1) أمان عرض البيانات — أولوية حرجة

- `js/app.js` يحتوي 33 موضعًا يستخدم `innerHTML =` وموضعًا واحدًا يستخدم `insertAdjacentHTML()`.
- توجد قوالب تدرج أسماء العملاء والموردين والأصناف والموظفين والملاحظات والعناوين والألوان والمقاسات وبيانات استيراد Excel مباشرة داخل HTML.
- أمثلة واضحة: `jDraw`، `drawL`، `nav`، `showInfo`، `vpt`، `tplFill`، `impCheck`.
- لا توجد دالة ترميز HTML عامة أو مكتبة تعقيم موثوقة في الواجهة، ولا يوجد اختبار XSS واضح في `tests/run.js`.
- النتيجة: احتمال Stored/Imported XSS إذا دخلت قيمة HTML/JavaScript ضارة من سجل أو ملف مستورد. لا ينبغي معالجة ذلك باستبدال عشوائي؛ المطلوب ترميز مخرجات حسب سياق HTML/attribute/URL، ثم اختبارات حمولة ضارة تغطي جميع القوالب.

### 2) مزامنة الحسابات والمخزون للموظفين — مانع تشغيل

- الكود الحالي يدعم مزامنة بعض الجداول التفصيلية، لكنه لا يثبت مزامنة كاملة مستقلة لدفتر الأستاذ وحركات المخزون لكل حساب موظف.
- `js/cloud-sync.js` نفسه يعرض رسالة بأن مزامنة القيود والحركات المحاسبية الكاملة لحساب الموظف لم تكتمل.
- PR #15 يحتوي تصميمًا متقدمًا للأثر المحاسبي/المخزني، baseline، tombstones والتعارضات، لكنه ما زال PR منفصلًا غير مدمج، ووصفه يقر بأن اختبارات Playwright الكاملة واختبارات جهازين لم تُنفذ عليه.
- لا تدمج PR #15 ولا تطبق migration الخاصة به على الإنتاج قبل اختبارها على QA واستكمال اختبار جهازين.

### 3) حدود الاختبارات الحالية

- تشغيل CI على الالتزام المرجعي: `137/137 checks passed`، و`npm run build` نجح.
- الاختبارات الحالية تزيل bootstrap الخاص بالمصادقة وملف `cloud-sync.js` من صفحة الاختبار؛ لذلك فهي لا تختبر مزامنة Supabase الحية أو جلسات مدير/موظف فعلية.
- لا يوجد اختبار XSS واضح في مجموعة الاختبارات الحالية.
- الاختبارات تغطي واجهة ووظائف محلية كثيرة (فواتير، مخزون، أوامر إنتاج، صلاحيات واجهة، PWA وموبايل)، لكنها ليست إثباتًا لتزامن سحابي صحيح بين جهازين.

### 4) Supabase الإنتاج — فحص قراءة فقط

- الجداول العامة الـ11 التي ظهرت في الفحص لديها RLS مفعّل.
- السياسات تستخدم `private.can_access_factory_owner` وتتحقق من هوية المستخدم والصلاحية المطلوبة؛ جدول `factory_state` مقيد بالمدير.
- امتيازات الجدول الخطرة التي سبق إزالتها غير ظاهرة ضمن منح `authenticated` الحالية؛ منح CRUD المعتادة ما زالت موجودة حسب الحاجة، و`profiles` لديه قراءة فقط في grants.
- Security Advisor: تحذير واحد فقط — Leaked Password Protection معطل. يتطلب تفعيله من إعدادات Auth إذا كانت الخطة تسمح بذلك، دون ترقية مدفوعة تلقائيًا.
- Performance Advisor أظهر 11 فهرسًا غير مستخدم. لا تحذفها الآن؛ قاعدة البيانات قليلة الاستخدام وقد تكون الفهارس لازمة عند نمو البيانات.
- Health Advisor لم يُظهر تحذيرات.
- قاعدة الإنتاج بها مستخدم Auth واحد وقت الفحص؛ لذلك لا يوجد إثبات حي لسلوك عدة موظفين.

### 5) وظائف Auth

- إنشاء حساب الموظف يتحقق من JWT ومن أن الملف `is_admin = true`، ويقيد الصلاحيات بقائمة مسموحة، ويجبر الموظف على تغيير كلمة المرور أول دخول.
- تغيير كلمة المرور الأولي يتحقق من المستخدم الحالي ومن أن الحساب غير إداري وأن علامة التغيير مطلوبة.
- لا يظهر مفتاح service-role في ملفات الواجهة؛ استخدامه محصور داخل Edge Functions بحسب الملفات التي تمت مراجعتها.

### 6) استعادة النسخة الاحتياطية إلى QA

- تشغيل Restore رقم 46 اجتاز فحوص الأسرار والوجهة والنسخة وB2 وفك التشفير، واستورد الجداول والبيانات حتى مرحلة Auth trigger.
- سبب الفشل المحدد: trigger على `auth.users` يستدعي `handle_new_user()` دون schema، بينما الدالة الفعلية هي `public.handle_new_user()`؛ لذلك لم يتمكن PostgreSQL من حل الاسم في search_path المستخدم أثناء الاستعادة.
- أضيفت معالجة لتأهيل اسم دالة trigger باستخدام schema المستخرج من تعريف الدالة، وأضيف fixture لاختبار هذا السلوك.
- فحص Workflow validation نجح على الالتزام المرجعي بعد الإصلاح. هذا لا يثبت نجاح استعادة فعلية.
- فحص QA بعد فشل التشغيل أكد أن قاعدة QA ما زالت فارغة: 0 جداول public، 0 مستخدمين Auth، 0 identities، 0 Storage buckets، ولا يوجد سجل migrations. المعاملة الواحدة تراجعت بالكامل.
- لم يُعاد تشغيل Restore بعد الإصلاح الأخير؛ لا تعلن اكتمال الاستعادة قبل نجاحها والتحقق من أعداد الصفوف وRLS والمستخدمين والمهاجرات والـ trigger.

### 7) النشر — ملاحظة سلامة مهمة

- ربط Vercel الحالي ينشر تلقائيًا من `main` إلى مشروعي `ms-factory` و`ms-factory-preview`.
- دفع إصلاحات Workflow إلى `main` أدى تلقائيًا إلى نشر Vercel Production على الالتزام `e9db69b...`، وظهر النشر READY مع ربط alias `ms-factory.vercel.app`.
- لم تتغير ملفات التطبيق نفسها في هذه الالتزامات؛ التغييرات كانت في Workflow وملف الاستعادة واختبار fixture. لكن هذا النشر لم يكن مقصودًا كجزء من المراجعة، ويجب عدم إجراء أي نشر أو تغيير alias إضافي دون موافقة صريحة.
- من الآن، يجب أن تكون إصلاحات التطبيق في فرع تدقيق/ميزة منفصل، لا على `main`، حتى لا يحدث نشر إنتاجي تلقائي آخر.

## قائمة الإصلاحات والاختبارات المطلوبة قبل اعتماد التشغيل

1. معالجة XSS في كل قوالب HTML باستخدام ترميز مخرجات مناسب للسياق، ثم إضافة اختبارات Stored XSS وExcel import payloads.
2. إكمال مزامنة دفتر الأستاذ وحركات المخزون للموظفين بصلاحيات مستقلة، مع idempotency وversion conflicts وtombstones وatomic writes.
3. دمج PR #15 فقط بعد مراجعة SQL، واختباره على نسخة QA المستعادة، واختبارات جهازين حقيقيين.
4. إتمام استعادة QA من النسخة الاحتياطية رقم 190 والتحقق المستقل من كل counts وRLS وAuth trigger.
5. اختبار دخول مدير وموظفين حقيقيين بصلاحيات مختلفة، ومنع الوصول المتبادل بين المصانع.
6. اختبار انقطاع الشبكة أثناء الحفظ والعودة والتكرار والتعارض وحذف السجلات.
7. اختبار Excel متعدد الشيتات على ملفات واقعية، ومطابقة أرصدة الافتتاح والفواتير والسندات والمخزون.
8. اختبار Android فعلي للكاميرا والباركود والطباعة والطابعة.
9. تفعيل Leaked Password Protection إن كان متاحًا ضمن الخطة الحالية.
10. منع النشر التلقائي للإصلاحات غير المعتمدة أو استخدام فرع منفصل حتى إتمام المراجعة.
