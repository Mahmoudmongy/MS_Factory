# تنفيذ تدعيم Supabase — 7 نوفمبر 2026

## النطاق
العمل على فرع `fix/supabase-auth-sync-hardening` من `main`. المشروع مستقل؛ لم تتم إضافة أي أدوار أو مسارات تشغيل للصنايعية أو رئيس العمال.

## تغييرات Supabase
- إضافة `profiles.is_admin` بصلاحية صريحة للمدير.
- حماية بيانات المصنع بسياسات RLS.
- إضافة `factory_state` للنسخة الكاملة من حالة التطبيق، وهي متاحة للمدير فقط لأنها تحتوي على بيانات كل الشاشات.
- إضافة Migration ثانية لتطبيق صلاحيات الموظفين على مستوى قاعدة البيانات، وليس إخفاء الواجهة فقط.
- جداول العملاء والموردين والمخزون والفواتير والإنتاج لها سياسات منفصلة حسب الصلاحية.
- حساب التقارير يتيح القراءة فقط، ولا يمنح الكتابة.
- إضافة فهارس للمفاتيح الأجنبية التي أبلغ عنها مستشار الأداء.
- وظيفة إنشاء حساب الموظف محمية بـ JWT وتتحقق من `profiles.is_admin` وتفرض قائمة صلاحيات معروفة.

## تغييرات الواجهة
- ربط قائمة الشاشات وصلاحيات التعديل والحذف بملف المستخدم المحمّل من Supabase.
- إخفاء الصفحة إلى أن يتم التحقق من جلسة الدخول وملف المستخدم.
- إيقاف إنشاء الحسابات العامة من شاشة الدخول؛ إنشاء حسابات الفريق من داخل حساب المدير فقط.
- مزامنة النسخة الكاملة مخصصة للمدير، بينما مزامنة الجداول التفصيلية تتبع صلاحيات الموظف.

## حدود مهمة
- لم يتم تشغيل Playwright أو `npm test` في بيئة تشغيل المشروع خلال هذه الجلسة.
- لم يتم تنفيذ تجربة دخول فعلية بحساب موظف بعد التغييرات.
- بنية التطبيق الحالية محلية أولاً، والنسخة الكاملة هي المرجع الأساسي. تغييرات الموظفين على الجداول التفصيلية لا تُدمج تلقائياً بعد في كل مكونات الحالة المحاسبية داخل نسخة المدير؛ لذلك لا ينبغي اعتبار تعدد المستخدمين والكتابة المتزامنة مكتملاً قبل اختبار/استكمال مزامنة القيود والحركات.
- حماية كلمات المرور المسربة ما زالت غير مفعلة في إعدادات Supabase Auth.
- تاريخ migrations في قاعدة البيانات يحتوي على migration التدعيم الحالية، ويحتاج توحيد baseline مع ملفات SQL القديمة قبل الاعتماد على `supabase db push`.
