# تدقيق الجاهزية التشغيلية — MS_Factory
**التاريخ:** 7 نوفمبر 2026  
**الحالة:** تدقيق أولي موثق — يستمر على مراحل  
**المستودع:** `Mahmoudmongy/MS_Factory`  
**قاعدة البيانات:** Supabase project `yvrislcbbhtruwdnuooz`

## 1. ملخص تنفيذي

البرنامج لديه أساس جيد: بناء Vite، اختبار متصفح عبر Playwright، تسجيل دخول Supabase، سياسات RLS، مزامنة بإصدارات وتعارضات، وواجهة PWA. لكنه **ليس جاهزًا بعد للاعتماد المحاسبي والتشغيل المتعدد المستخدمين بالكامل**.

نجاح اختبارات الواجهة والبناء لا يثبت وحده صحة المزامنة الحية أو كل القيود المالية أو استعادة النسخ الاحتياطية. لذلك يجب استكمال اختبارات البيئة الحقيقية قبل التشغيل اليومي.

## 2. الحالة التي تم التحقق منها

- فرع `main` عند الالتزام `b186abbf3bc9b8f446050003439272a7160dd16b`.
- آخر GitHub Actions على هذا الالتزام: اختبارات المشروع والبناء ناجحان.
- المشروع مبني باستخدام Vite، والواجهة الحالية تطبيق PWA.
- مشروع Supabase في حالة `ACTIVE_HEALTHY`، وقاعدة PostgreSQL 17.11.
- يوجد 11 جدولًا في مخطط `public`، وRLS مفعّل على الجداول الإحدى عشر.
- يوجد مستخدم Auth واحد وملف مستخدم واحد؛ لذلك لم يتم إثبات سلوك النظام مع حسابات موظفين حقيقية متعددة.
- نسخة `factory_state` واحدة تحتوي بيانات حالة التطبيق. المراجعة قرأت أعداد السجلات ومفاتيح JSON فقط، ولم تعرض محتوى السجلات.

## 4. الأمان والصلاحيات

### ما تم التحقق منه
- RLS مفعّل على جميع جداول البيانات العامة.
- السياسات الحالية تستهدف `authenticated` ولا توجد سياسات قراءة/كتابة عامة للمجهولين على جداول المصنع.
- الملف الكامل `factory_state` مخصص للمدير.
- ملف المستخدم مقيد: المستخدم يستطيع قراءة ملفه، وتعديل الاسم الظاهر فقط؛ لا يستطيع تعديل صلاحياته أو صفة المدير.
- دوال إنشاء حساب الموظف وتغيير كلمة المرور الأولية تتطلب JWT. إنشاء الحساب يفحص أن المنفذ مدير نظام.
- مفتاح `service_role` مستخدم داخل Edge Functions فقط، ولم يظهر ضمن ملفات الواجهة التي تمت مراجعتها.

### مشكلة أمنية اكتُشفت وعولجت في قاعدة البيانات
قبل التدعيم، كان دور `authenticated` يملك امتيازات جدولية إضافية على 10 جداول: `TRUNCATE` و`TRIGGER` و`REFERENCES` و`MAINTAIN`. امتياز `TRUNCATE` لا يخضع لسياسات RLS، لذلك لم يكن ينبغي أن يكون متاحًا لعميل المتصفح.

تم تطبيق migration إضافي برقم:
`20261107173208_revoke_authenticated_elevated_table_privileges`

وتم التحقق بعد تطبيقه من أن الامتيازات الأربعة أصبحت غير متاحة على جميع جداول `public`، مع بقاء صلاحيات CRUD التي يحتاجها البرنامج، وبقاء قيود جدول `profiles` الأشد. كما أضيف إلغاء لهذه الامتيازات من الصلاحيات الافتراضية للجداول الجديدة.

**متابعة مطلوبة:** migration موجود في فرع التدقيق، ويجب دمجه في `main` حتى يظل سجل GitHub مطابقًا تمامًا لما طُبق على قاعدة البيانات.

### تحذير أمني متبقٍ
مستشار Supabase يعرض تحذيرًا بأن فحص كلمات المرور المسربة غير مفعّل. يجب تفعيله من إعدادات Auth عندما تسمح الخطة الحالية بذلك؛ لا يتم تغيير الخطة أو فرض رسوم دون موافقة.

## 5. المزامنة والعمل دون إنترنت

### ما يعمل في التصميم الحالي
- يحفظ التطبيق الحالة المحلية في `localStorage` بالمفتاح `mgr6`.
- توجد علامة انتظار للمزامنة ومحاولات إعادة عند عودة الاتصال والتركيز والظهور الدوري.
- نسخة المدير الكاملة تستخدم RPC بإصدار متوقع لمنع الكتابة فوق نسخة سحابية أحدث دون تنبيه.
- مزامنة التفاصيل تدعم الأطراف والأصناف والفواتير والمرتجعات والسندات وأوامر الإنتاج، مع معرفات خارجية وتحقق من التعارضات.
- Service Worker يخزن ملفات غلاف التطبيق والأصول الثابتة، ولا يخزن استجابات Supabase أو بيانات المستخدمين في Cache المتصفح.

### ما لم يثبت اكتماله
- لا توجد قاعدة بيانات محلية من نوع IndexedDB؛ البيانات التشغيلية تبقى في `localStorage`.
- مزامنة الموظفين موسومة في الكود بأنها جزئية.
- القيود ودفتر الأستاذ وحركات المخزون وبعض بيانات التشغيل محفوظة ضمن النسخة الكاملة للمدير، وليست مكتملة كمزامنة تفصيلية مستقلة لكل حساب موظف.
- لم يتم اختبار تسجيل دخول حي لموظف، ولا تعديل متزامن فعلي بين جهازين أو مستخدمين.
- لم يتم اختبار سيناريو تعارض بين جهازين متصلين ثم استعادة البيانات فعليًا من نسخة احتياطية.

**القرار:** لا نعتمد حتى الآن على عدة موظفين لإدخال قيود وحركات محاسبية متزامنة قبل إنهاء هذا الجزء واختباره.

## 6. وظائف البرنامج والاختبارات

المشروع يحتوي اختبارات متصفح فعلية عبر Playwright، منها سيناريوهات فواتير ومخزون وسندات وعملات وأوامر إنتاج وصلاحيات وموبايل وPWA. ونجح آخر تشغيل CI على `main`.

لكن النطاق غير المغطى بما يكفي:

1. تسجيل دخول حي بحساب مدير وموظف واختبار صلاحيات قاعدة البيانات في كل حالة.
2. دورة معاملات كاملة على Supabase ثم التأكد من استعادتها على جهاز آخر.
3. اختبارات ضغطتين متزامنتين وحالات فشل الشبكة أثناء منتصف الحفظ.
4. استعادة نسخة احتياطية كاملة في بيئة منفصلة.
5. اختبار فعلي على هاتف Android وطباعة فعلية وطابعة ملصقات.
6. اختبار Excel `xlsx` فعليًا مع ملف قديم متعدد الشيتات؛ الاختبارات الحالية لا تثبت ترحيل السجل المحاسبي التاريخي.

## 7. فجوات يجب إغلاقها قبل التشغيل الكامل

| الأولوية | الفجوة | المطلوب |
|---|---|---|
| حرجة | عرض بيانات المستخدم مباشرة داخل HTML في مواضع متعددة | مراجعة شاملة لمنع XSS، مع ترميز النصوص والقيم، ثم اختبارات إدخال ضارة |
| حرجة | المزامنة المحاسبية للموظفين متعددة الأجهزة غير مكتملة | تصميم مزامنة معاملات دفترية وحركات مخزون بمعرف عملية فريد ومعاملة قاعدة بيانات واحدة |
| عالية | الاستيراد الحالي يغطي البيانات الأساسية فقط | استيراد تاريخي للفواتير والسندات والأرصدة والقيود وحركات المخزون بعد مطابقة نموذج الملف القديم |
| عالية | لا يوجد إثبات لاستعادة نسخة احتياطية | سياسة نسخ احتياطي خارجية واختبار استعادة موثق |
| عالية | لم تُختبر حسابات متعددة حقيقية | حسابات اختبار منفصلة مع مصفوفة صلاحيات واختبارات RLS حية |
| متوسطة | التخزين المحلي `localStorage` | تقييم IndexedDB وحدود التخزين واستعادة الطابور |
| متوسطة | التصدير الحالي CSV متوافق مع Excel وليس ملف XLSX كاملًا | إخراج XLSX حقيقي عند الحاجة |
| متوسطة | تجربة الموبايل لم تُختبر على جهاز فعلي | اختبار Android، لوحة المفاتيح، الكاميرا والطباعة |

### ملاحظة حول أمان عرض البيانات
توجد مواضع تنشئ واجهة الشاشة عبر `innerHTML` وتدرج أسماء وعناوين وبيانات مدخلة من المستخدم مباشرة. هذه نقطة مراجعة أمنية جدية؛ يجب إنهاؤها قبل إتاحة إدخال بيانات من مصادر خارجية أو استيراد ملفات غير موثوقة.

## 8. النشر

- رابط الإنتاج `https://ms-factory.vercel.app` كان يعرض بناء Production أقدم من آخر التعديلات التي تم دمجها على `main`.
- نُشرت نسخة Preview من فرع التدقيق للتأكد من أن ملفات البناء الجديدة تُقدم عبر Vercel.
- فرع Preview لا يحتوي إعدادات `VITE_SUPABASE_URL` و`VITE_SUPABASE_ANON_KEY`؛ لذلك لا يُستخدم حاليًا لتسجيل الدخول أو إدخال بيانات فعلية.
- لا يتم نسخ إعدادات الإنتاج إلى Preview قبل توفير عزل مناسب لقاعدة البيانات، حتى لا تتحول بيئة المعاينة إلى كتابة مباشرة على بيانات التشغيل.

## 9. ترتيب العمل التالي

1. دمج migration إزالة الامتيازات الإضافية في سجل GitHub، بعد نجاح CI.
2. إنهاء معالجة XSS والترميز الآمن لكل البيانات المعروضة.
3. بناء اختبار حي لحسابين: مدير وموظف بصلاحية محدودة.
4. إغلاق فجوة مزامنة الدفتر والأرصدة وحركات المخزون للموظفين، مع منع التكرار والتعارض.
5. إنشاء مسار نسخ احتياطي واستعادة مجرّب.
6. بناء استيراد تاريخي تجريبي من ملف البرنامج القديم ومطابقة الإجماليات.
7. اختبار Android والطباعة والسيناريوهات التشغيلية الكاملة.
8. بعد اجتياز بوابات القبول، نشر الإصدار Production واعتماد بدء التشغيل.
